# Phase 0 Research: Multiple Git Credentials per Domain

No `NEEDS CLARIFICATION` markers remain in the Technical Context (language, dependencies, storage, and testing approach all follow directly from the constitution and the existing `GitProperties`/`GitService` code this feature extends). The open questions below are implementation-level decisions needed to turn the spec's functional requirements into a concrete design; none of them change spec-level behavior already agreed in `spec.md`'s Clarifications section.

## D1: Config field name and shape for the new scope path

- **Decision**: Add a single optional string field named `path` to both `GitPropertiesDto.TrustedPrivateGitRepoDto` and `GitProperties.TrustedPrivateGitRepo`. No separate "scope kind" enum/discriminator field.
- **Rationale**: Whether a `path` value acts as a repository-specific match or a project/group prefix match is entirely determined at resolution time by comparing it against the target repository's path (exact match vs. segment-prefix match — see D3). Storing an explicit kind would duplicate information already implied by the comparison and could drift from reality (e.g. an operator labels an entry "project" but it happens to equal a full repo path). A single field is simpler and cannot be inconsistent with itself.
- **Alternatives considered**: A `scopeType: REPOSITORY|PROJECT|DOMAIN` enum alongside `path` — rejected as redundant per above. Separate `repositoryPath` and `projectPath` fields — rejected, forces the operator to pick the "right" field name for what is really one comparison.

## D2: Path normalization for matching and duplicate-scope detection

- **Decision**: Before comparison (both for matching in `GitService` and duplicate-scope validation in `GitConfiguration`), normalize a configured `path` and a URL-derived path by: trimming leading/trailing `/`, and stripping a trailing `.git` suffix. Host comparison stays case-insensitive (existing behavior implicitly relies on typical lowercase git hosts; no change). Path comparison stays case-sensitive (git repository paths are case-sensitive on virtually all hosting providers).
- **Rationale**: Operators will naturally write `team/service-a`, `/team/service-a/`, or `team/service-a.git` interchangeably; without normalization these would be treated as different scopes, silently breaking matching (e.g. a build cloning `.../team/service-a.git` wouldn't match an entry configured as `team/service-a`) or evading the duplicate-scope validation (two entries that are actually the same scope written differently would both pass validation and then tie unpredictably at resolution time).
- **Alternatives considered**: No normalization (reject anything not written in one canonical form) — rejected as a foot-gun that contradicts FR-005's goal of catching ambiguity at startup, since near-duplicate scopes would slip through untouched.

## D3: Specificity ranking algorithm

- **Decision**: For a given repository URL, extract `(host, path)`. For each configured entry, compute whether it matches and, if so, a specificity tuple `(hostRank, hostLength, pathRank, pathLength)`:
  - `hostRank`: `0` if the entry's configured host equals the URL's host exactly; `1` if the URL's host is a subdomain of the entry's configured host (existing `endsWith("." + host)` rule, preserved per FR-003a).
  - `hostLength`: length of the entry's configured host — longer means a closer parent domain. It is a no-op for exact-host matches (where it always equals the URL host's length) and therefore only discriminates between two parent-domain matches, where it deliberately outranks path specificity (see the note below).
  - `pathRank`: `0` if the entry has no `path` (domain-wide); `1` if the entry's `path` is a strict segment-prefix of the URL's path (project/group scope); `2` if the entry's `path` equals the URL's path exactly (repository-specific).
  - `pathLength`: length of the entry's normalized `path` (used only to break ties between two segment-prefix matches of different depth, e.g. nested groups — longer wins).
  - Among all matching entries, pick the one with the lexicographically **best** tuple ordered by: `hostRank` ascending (0 beats 1) first, then `hostLength` descending (closest parent domain), then `pathRank` descending (2 beats 1 beats 0), then `pathLength` descending.
- **Rationale**: This directly encodes the precedence spelled out in spec FR-003 (exact-host beats subdomain-inherited, regardless of path specificity — `hostRank` is compared first) and FR-002a/FR-003a (segment-boundary matching, repo-exact beats project-prefix, longest project-prefix wins among nested groups). Computing a tuple once per candidate keeps the resolution a simple sort/min rather than nested conditionals, and mirrors the existing single-pass `findMatchingTrustedRepo` loop shape.
- **Alternatives considered**: Iterate entries in configuration order and take the first match (today's behavior) — rejected, this is exactly the ordering-dependent behavior the spec (User Story 3, SC-003) asks to remove. Sort the whole list once at startup by specificity and always take the first structural match — rejected as unnecessary extra state; matching is cheap enough (list is operator-sized) to compute the tuple per lookup.
- **Note on cross-host subdomain ties**: If two *different* configured hosts could both match a URL via subdomain inheritance (e.g. entries for `example.com` and `api.example.com` both plausibly match `sub.api.example.com`), the more specific (longer) configured host is preferred, ahead of path specificity — "closest domain first, then most specific path within it", a natural extension of "most specific wins" that was already implicit but under-specified in the pre-existing single-credential-per-host code (which took first-match-in-list-order). This is a strict improvement over today's behavior for a case that only manifests once multiple entries genuinely coexist, so it doesn't change behavior for any configuration that resolves unambiguously today.

## D4: Duplicate-scope validation

- **Decision**: After parsing and normalizing (D2) all entries, group by exact `(normalized host, normalized path-or-null, authentication type)` triple, where authentication type is `SSH` for entries with an SSH key and `HTTPS/HTTP` for entries with `user`/`token` (an entry with both is counted under both). If any group has more than one entry, fail startup with `IllegalArgumentException` listing the conflicting `(host, path)`, the authentication type and, for operator diagnosability, the index/position of each conflicting entry in the source list.
- **Rationale**: Directly implements FR-005. Grouping by the literal configured `(host, path)` pair (not by "what URLs could this match") is a bounded, unambiguous check — it does not try to detect every possible overlap (e.g. it doesn't flag `team` vs. `team/sub`, which is a legitimate nested-specificity case per the Edge Cases section, not a conflict).
- **Rationale for keying on authentication type**: An SSH-only and an HTTPS-only entry at the same `(host, path)` are not ambiguous — resolution filters candidates by the URL's protocol before ranking them, so each URL sees exactly one of the two. This is also the pre-existing shape of a host that is cloned both ways, so keying only on `(host, path)` would have failed such a configuration at startup on upgrade.
- **Alternatives considered**: Flagging any pair of entries whose scopes could ever both match the same URL (i.e. any overlap, not just identical scopes) — rejected; that would reject the legitimate and expected nested/overlapping configurations from User Stories 1-3 (e.g. a domain-wide fallback plus a project-scoped entry plus a repository-specific entry are *meant* to overlap).

## D5: SSH vs. HTTPS path extraction

- **Decision**: Reuse the existing `extractHostFromUrl`/`extractHostFromSshUrl`/`extractHostFromHttpUrl` split in `GitService`, and add a parallel `extractPathFromUrl` that mirrors the same HTTPS-vs-SSH branching: for HTTPS/HTTP URLs, `URI.create(gitUrl).getPath()`; for `git@host:path` SSH URLs, everything after the first `:`; for `ssh://[git@]host/path` URLs, everything after the host segment. Path normalization (D2) is applied afterward uniformly.
- **Rationale**: The URL parsing surface for host extraction already exists and is well-tested implicitly by today's single-credential behavior; extending it with a path counterpart keeps the two forms (HTTPS/SSH) consistent and avoids introducing a second URL-parsing strategy.
- **Alternatives considered**: A full `GitUrl` value object encapsulating host+path+scheme — considered for clarity, but rejected as unnecessary ceremony for two small extraction methods used only inside `GitService`.
