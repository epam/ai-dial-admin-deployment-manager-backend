## REST API

The Deployment Manager Backend exposes REST endpoints under the `/api/v1` prefix. The OpenAPI UI is served at `/swagger-ui/index.html` (spec at `/v3/api-docs`).

### Main API Endpoints

| Path | Purpose |
|---|---|
| `/api/v1/images/definitions` | Image definition CRUD, grouped/versions views, revisions and rollback |
| `/api/v1/images/builds` | Trigger/stop builds, status, details, build logs (SSE) |
| `/api/v1/deployments` | Deployment CRUD, deploy/undeploy, duplicate, change image, pods & logs, events stream (SSE), metrics, revisions and rollback |
| `/api/v1/deployments/mcp` | MCP server introspection — tools, resources, prompts, tool calls |
| `/api/v1/configs` | Export / import of configuration (with previews) |
| `/api/v1/activities`, `/api/v1/history/revisions` | Audit activity feed and revision history |
| `/api/v1/global-whitelist` | Global domain whitelist for image builds |
| `/api/v1/node-pools` | Configured node pools |
| `/api/v1/mcp-registry/servers` | MCP registry browser |
| `/api/v1/huggingface/models` | HuggingFace model search and metadata |
| `/api/v1/topics` | Topic listing |
| `/api/v1/security-info` | Security mode information for clients |
| `/api/v1/disposable` | Disposable resource cleanup |
| `/api/v1/health` | Health check (unauthenticated) |

### Internal Endpoints

- `/api/internal/v1/deployments` - Internal deployment endpoints used by the admin backend (unauthenticated — restrict at the network level)

## Build and Development Commands

### Building

```bash
# Full clean build (includes tests and checkstyle)
./gradlew clean build

# Build without tests
./gradlew build -x test

# Build Docker image
docker build -t aidial/ai-dial-admin-deployment-manager-backend:latest .

# Regenerate docs/db-schema.md from the current migrations
./gradlew generateDbSchema
```

Model classes for the CRDs in `src/main/resources/kubernetes/crd` (KServe `InferenceService`, `CiliumNetworkPolicy`) are generated by the fabric8 `java-generator` plugin (`crd2java`, runs before every compilation) into `build/generated/sources/fabric8JavaGenerator`. Knative types come from the `io.fabric8:knative-client` library and are not generated.

### Running

```bash
# Run the application with Gradle
./gradlew bootRun

# Run with Docker Compose (development mode)
cd local_env
docker compose up

# This starts:
# - deployment-manager-backend (main application, built from the repo Dockerfile;
#   debug port 15006, Prometheus metrics 9464, ~/.kube mounted)
# - postgres (PostgreSQL)
# - sqlserver (MS SQL Server)
# Keycloak is started only with the `keycloak` profile:
docker compose --profile keycloak up

# Stop Docker Compose
docker compose down
```

The application uses H2 by default; switch with `DATASOURCE_VENDOR` (`H2`, `POSTGRES`, `MS_SQL_SERVER`) in `local_env/docker-compose.yml`.

## Testing

```bash
# Fast feedback — everything except the Postgres / SQL Server functional suites
./gradlew testFast

# Full suite — includes Postgres and SQL Server via Testcontainers (requires Docker)
./gradlew test

# Run a specific test class
./gradlew testFast --tests "com.epam.aidial.deployment.manager.service.ImageDefinitionServiceTest"

# Run the H2 functional suite
./gradlew testFast --tests "com.epam.aidial.deployment.manager.functional.H2FunctionalTests"

# Run tests with a pattern
./gradlew testFast --tests "*ControllerTest"
```

Functional tests in `functional/tests/` are abstract and executed through the per-database suites (`H2FunctionalTests`, `PostgresFunctionalTests`, `SqlServerFunctionalTests`), so the same scenarios run against every supported vendor. `K8sFunctionalTests` runs real cluster operations and is skipped unless `SPRING_PROFILES_ACTIVE=k8s-local` (prerequisites are listed in its Javadoc). ArchUnit tests in `architecture/` enforce layering rules.

## Architecture

The code follows a layered architecture (`web` → `service` → `dao` / `kubernetes`); each layer has its own `CLAUDE.md` with layer-specific rules. See the constitution for the full rule set.

### Core Components

**Pipeline-Based Image Building**: Container images are built with BuildKit in Kubernetes jobs (rootful or rootless). Pipelines include building from Git (`ImageBuildFromGitPipeline`), copying an existing image into the target registry via Skopeo (`ImageCopyPipeline`), and wrapping an image (`ImageWrapperBuildPipeline`). For STDIO MCP servers, the wrapper pipeline inserts an HTTP-to-STDIO proxy executable into the user-provided base image; the image's Linux distribution (Alpine vs Debian) is detected to select the matching proxy executable. Builds can be stopped while in flight.

**Deployment Runtimes**: Deployments are managed by a runtime-specific `DeploymentManager`:
- `KnativeDeploymentManager` — Knative Serving services for MCP, interceptor, adapter and application deployments, with auto-scaling.
- `InferenceDeploymentManager` — KServe `InferenceService` for HuggingFace model deployments; text-classification models get a chained transformer container.

Manifests are generated in `service/manifest` from configurable templates (`app.knative-service-config`, `app.inference-service-config`, ...), with optional Cilium network policies, node-pool scheduling primitives and auto-provisioned pull secrets. Deployment state is reconciled with the cluster on startup, via informers and on a schedule.

**Disposable Resource Management**: Kubernetes resources are tracked by group ID with lifecycle states (TEMPORARY, STABLE, TO_CLEANUP) and cleaned up by scheduled jobs coordinated with ShedLock.

### Key Service Patterns

- **McpService**: Manages Model Context Protocol client connections (via `McpClientFactory`) and exposes tools, resources, prompts and tool calls.
- **DeploymentService**: Deployment CRUD and lifecycle; sensitive environment variables become Kubernetes Secrets.
- **ImageBuildRunner / ImageBuildStopService**: Run and stop image build pipelines, streaming status and logs over SSE.
- **Audit services** (`service/audit`): Activity feed, revision history and rollback built on Hibernate Envers.

### Database Architecture

**Polymorphic Entities**: Image definitions (MCP, interceptor, adapter, application) and deployments (MCP, interceptor, adapter, application, inference) are modelled as JPA `JOINED` inheritance hierarchies — a base table plus one table per subtype.

**Auditing**: Hibernate Envers audit tables plus a denormalized activity feed.

**Resource Tracking**: DisposableResource entities track Kubernetes resources by group ID for cleanup.

**Database Support**: H2 (with AES file encryption; development only), PostgreSQL, and MS SQL Server. Flyway SQL migrations live in `src/main/resources/db/migration/<VENDOR>/` and every schema change needs a script for each vendor; Java migrations for data transformations live in `src/main/java/db/migration/<VENDOR>/`. See `specs/database-and-migrations/spec.md`.

## Development Notes

### Sensitive Data Handling

Sensitive environment variables are converted to Kubernetes Secrets. These secrets are tracked as disposable resources and cleaned up automatically, and their values are sanitized from configuration exports.

### Kubernetes Integration

Supports both config file and token-based K8s authentication with context switching:
- `K8S_CONNECT_TYPE=CONFIG_FILE` with kubeconfig (default: `~/.kube/config`)
- `K8S_CONNECT_TYPE=TOKEN` with master URL (`K8S_MASTER_URL`) and OAuth token (`K8S_OAUTH_TOKEN`)

Knative support is controlled by `K8S_KNATIVE_ENABLED` (default `true`), KServe by `K8S_KSERVE_ENABLED` (default `false`).

### Docker Registry

Configure registry authentication via `DOCKER_REGISTRY_AUTH`:
- `NONE` - No authentication
- `BASIC` - Basic authentication (requires `DOCKER_REGISTRY_USER` and `DOCKER_REGISTRY_PASSWORD`)

Additional read-only registries can be configured with `TRUSTED_PRIVATE_REGISTRIES`.

## Configuration for Development

### Development Mode

For local development without authentication, set:
```bash
CONFIG_REST_SECURITY_MODE=none
```

This is the default and is already set in `local_env/docker-compose.yml`.

### H2 Database Credentials

For local development with H2 database, default credentials are provided in `local_env/docker-compose.yml`.

To generate new H2 encryption credentials, you can use:

1. **Java Test Class**: `com.epam.aidial.deployment.manager.encryption.GenerateSecretsTest`

2. **Scripts** from the [main admin repo](https://github.com/epam/ai-dial-admin-backend/tree/development/secrets-utils):
   ```bash
   python secrets-utils/keys_generator.py
   # or
   ./secrets-utils/generate_h2_secrets.sh
   ```
   These generate values for:
   - `H2_DATASOURCE_PASSWORD`
   - `H2_DATASOURCE_MASTER_KEY`
   - `H2_DATASOURCE_ENCRYPTED_FILE_KEY`

For complete configuration documentation, see [Configuration Documentation](configuration.md).
